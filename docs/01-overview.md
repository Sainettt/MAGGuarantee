# 01. Что делает система

> Бизнес-обзор предметной области. Без привязки к технологиям. Это то, что должно работать в новом приложении.

## Назначение

**MagTrans Guarantee (MAGGuarantee)** — внутренняя система управления **гарантией километража** для логистической компании MagTrans. Перевозчики (subcontractors) подают заявления (`wniosek`) на компенсацию, когда автомобиль за период проехал меньше гарантированного количества километров. Система рассчитывает доплату в EUR на основе:

- дневного лимита километров (по неделям ISO — у каждой недели своё значение),
- ставки EUR/км (тоже по неделям),
- субботней гарантии — км за субботу недели (понедельный опт-ин `kmPerSaturday`, оцениваются по той же ставке `ratePerKm`),
- учёта выходных и праздничных дней ЕС (включая Пасху),
- корректировки на простой / сервис.

Помимо ядра «гарантия», система покрывает:

- **CRUD автопарка** — автомобили, прицепы, водители каждого перевозчика.
- **Модуль делегаций (выездов)** — учёт фактических рейсов: `zgloszony` → `w_trasie` → `zjechal`.
- **Рекламации** — частичный пересмотр уже принятого решения.
- **Email-нотификации** (треды по `nrZgl`).
- **Audit-лог** всех критических операций.
- **Двухфакторная авторизация** через 6-значный код по email.

## Ключевые бизнес-процессы

### 1. Подача заявления (wniosek)

```
Перевозчик выбирает выезд (только уже zjechał) и заполняет форму
  → САМ указывает период (dateStart/dateEnd), часы (timeFrom/timeTo) и пробег
  → расчёт km гарантии (calcKmGwarant) по заявленным значениям
  → сохранение со статусом NA_WERYFIKACJI
  → email админу + перевозчику + внутренним сотрудникам (planista, opiekun, lider)
```

Подать заявление можно только по выезду в статусе `zjechał`.

**Перевозчик заявляет факты сам** (решение заказчика 2026-07-30, отменяет прежнюю деривацию из выезда). Причина: деньги платятся по пробегу из **SpedTrans**, а дневные километры верификатора берутся из другой внешней системы — цифры никогда не совпадают. Поэтому перевозчик указывает свои, а `pracownik` при верификации сверяет их с данными верификатора, которые показываются рядом в модалке, и правит при необходимости.

Ограничения на заявленные значения намеренно минимальны:

| Поле | Правило |
|---|---|
| `dateStart` | не раньше даты выезда, заявленной при zgłoszeniu (422 `CLAIM_DATE_BEFORE_DEPARTURE`) |
| `dateEnd` | не ограничена фактическим возвратом — вернуться можно и раньше, и на несколько дней позже |
| `timeFrom` / `timeTo` | обязательны |
| `mileage` | свободный; проверяется только `> 0` и потолок среднесуточного пробега |

**Срок подачи** (`max_days_after_unloading`) считается от фактического возврата, зафиксированного верификатором, а не от даты, введённой перевозчиком — иначе правило можно было бы обойти, вписав дату посвежее.

### 2. Верификация заявления

```
Сотрудник (admin/pracownik) открывает заявление
  → корректирует данные
  → live re-calc (kmGwarant, doplata)
  → zapis weryfikacji (checkpoint); если doplata > próg —
    АВТО-переход в OCZEKUJE_NA_AUTORYZACJĘ + email Maksim'у
  → решение: ZAAKCEPTOWANO / ODRZUCONO
  → email перевозчику с цветным header (по статусу)
  → email внутренним сотрудникам
```

### 3. Делегация (выезд)

```
Перевозчик регистрирует выезд (auto, kierowca, naczepa, маршрут, datetime выезда)
  → status: zgloszony
Верификатор:
  → markInTransit  → задаёт ТОЧНЫЙ datetime выезда (actualDepartureAt) → status: w_trasie
  → markReturned   → задаёт ТОЧНЫЙ datetime съезда (actualReturnAt)    → status: zjechal
                   → автообновление поля "OstatnioJezdzilo" у авто
```

Оба перехода несут полный datetime (дата + время): именно верификатор фиксирует фактические моменты выезда и съезда. Из этих времён затем деривируются часы заявления (`wniosek`).

Любой статус может быть `anulowany`. Перевозчик может анулировать только `zgloszony`-выезды, верификатор — любые.

### 4. Авторизация (login)

```
1) login + password → проверка
   - генерируется 6-значный код, кладётся в кеш на 10 мин
   - отправляется email с кодом
2) ввод кода → проверка
   - 5 неверных попыток → блокировка на 5 мин
   - валидный → user-объект в сессии
3) Frontend показывает экран по роли
```

### 5. Рекламация

> ⚠️ Переработано 2026-07-31 (решения заказчика). Рекламация — это **спор о деньгах**, а не повторная подача заявления: правятся только сумма и обоснование, никакие данные wniosku перевозчик не переписывает.

**Подача (перевозчик, `POST /claims/:nrZgl/reklamacja`).** Одна рекламация на wniosek **навсегда** (флаг `reklamacjaSubmitted` никогда не сбрасывается), только на **рассмотренный** wniosek (`ZAAKCEPTOWANO`/`ODRZUCONO`), в течение **48 часов** от `statusChangedAt`. Тело — только `tresc` (обязательное обоснование) и `kwotaReklamacji`, где `0 < kwota ≤ maxAmount`:

```
maxAmount = (origPaymentEur ?? paymentEur) − (status === 'ZAAKCEPTOWANO' ? (amountApproved ?? 0) : 0)
```

То есть «сколько просил минус сколько реально заплатили» — непокрытый остаток. Сравнения — с точностью до цента, строго (легаси-допуска `+1 €` больше нет). Если `maxAmount ≤ 0` (выплата покрыла всю запрошенную сумму) — подача заблокирована. Формула живёт в **одном** месте — `packages/shared/src/domain/reklamacja-rules.ts` (`getReklamacjaEligibility`), её зовут и api, и web-форма.

При подаче: `status = REKLAMACJA`, `statusBeforeReklamacja = status` (куда потом вернёмся), `reklamacjaSubmittedAt = now`, плюс «зеркало» оригинальных данных (`origDateStart`, `origDateEnd`, `origMileage`, `origHoursAdjusted`) — исторический слепок, см. [19-known-quirks.md](19-known-quirks.md#reklamacja-mirror). Письма: всем активным `admin` + `pracownik` (`reklamacja-internal-submitted`) и подтверждение перевозчику (`reklamacja-carrier-submitted`).

**Решение (`pracownik`/`admin`, `PATCH /claims/:nrZgl` с `targetStatus: REKLAMACJA_ZAAKCEPTOWANO | REKLAMACJA_ODRZUCONO`).**

- **UZNANA** — требует `reklamacjaOrderNumber` («Nr zlecenia», под которым платится dopłata; независим от `orderNumber` самого wniosku). Выплачивается **ровно** carrier-ская `reklamacjaAmount` — сотрудник сумму не назначает. `comment` опционален → `reklamacjaResponse`.
- **ODRZUCONA** — требует `comment` (обоснование отказа) → `reklamacjaResponse`.
- При **обоих** исходах `status` **возвращается** в `statusBeforeReklamacja`: решение по самому wniosku не переигрывается, отдельно платится (или не платится) рекламация. Исход хранится **только** в `reklamacjaResolution` (`UZNANA`/`ODRZUCONA`) — из статуса его выводить нельзя. Плюс `reklamacjaDecidedAt` / `reklamacjaDecidedById`.
- Решение **никогда** не трогает `amountApproved`, `orderNumber`, `orderDate`, `paymentEur` и claim-level `decidedById`; km-calc не пересчитывается (суммы заморожены). Порог Maksima и чекпоинт верификации на этот путь не распространяются. Письмо перевозчику — `reklamacja-carrier-decision` (тон по исходу).

## Ключевые формулы (бизнес-правила)

### Расчёт гарантии (`calcKmGwarant`)

> ⚠️ С 2026-10-29 лимиты **понедельные** (раньше — помесячные, с правилом «нечётных суббот месяца»). Неделя — **ISO 8601**: пн–вс, номера 1–52/53, неделя принадлежит году, на который приходится её четверг (2026-W01 = 29.12.2025–04.01.2026; 2026-W53 = 28.12.2026–03.01.2027). Ключ недели — `YYYY-Www` (`2026-W23`). Почему и как переносились данные — [17-migration-roadmap.md](17-migration-roadmap.md) «Доработка (2026-10-29)».

Для интервала `[dateStart, dateEnd]`:

1. Разбить интервал на недели ISO. Первая и последняя неделя обычно неполные — в них попадают только дни периода.
2. Для каждой недели посчитать **будние дни** (пн–пт), исключая:
   - воскресенья (всегда) и субботу (кроме зачётной — см. шаг 4),
   - праздники EU (`getEUBanDays`),
   - пасхальный понедельник (`calcEaster` + 1).
3. Умножить будние дни на лимит недели `km/day` из таблицы лимитов. **Три состояния лимита** (2026-09-20, без изменений): строки/колонки нет (`NULL`) → fallback 540 км/дн и 0,5 €/км, подставляемый **пополево**; `0` → гарантия на неделю **выключена осознанно** (неделя даёт 0 км); `> 0` → значение. Админ переключает это через `PUT /limits/:isoWeek` или `POST /limits/bulk` (см. [13-api-design.md](13-api-design.md#limits)).
4. **Суббота недели** (понедельный опт-ин). Если у недели `kmPerSaturday > 0`, её суббота засчитывается — при условии, что она внутри периода. Какие субботы оплачиваются, решает админ, выставляя значение по неделям; правила «1-я / 3-я / 5-я суббота месяца» больше нет. Суббота считается **целым днём** (`+1` к дням, без пропорции по часам) и приносит `kmPerSaturday` км по ставке **той же недели** `ratePerKm` (отдельной EUR-ставки нет). Суббота на EU-ban / празднике **не** оплачивается и **не** считается днём (уходит в `excludedDays`). При `kmPerSaturday = 0 / NULL` суббота исключена полностью (fallback субботы — `0`).
5. Учесть **дробные дни** (если интервал начинается / заканчивается посреди буднего дня — пропорция от часов; суббота всегда целая).
6. Скорректировать на часы простоя/сервиса — пропорционально между неделями с `kmPerDay > 0`, только по будним дням.
7. Вычислить **взвешенную ставку** EUR/km по неделям (вес — км недели).
8. Вернуть `{totalDays, kmGwarant, breakdown[], ratePerKmEffective}`; `breakdown[]` — **одна строка на неделю ISO**, которую задел период.

### Расчёт доплаты

Пробег перевозчик заявляет **одной суммой** за весь период, а гарантия считается по неделям. Пока у **всех** недель периода включена гарантия будней (`kmPerDay > 0`), этого достаточно. Как только есть неделя с `kmPerDay = 0`, её километры нельзя вычитать из гарантии включённой недели, а сколько их было — из одной суммы не узнать. Такой **смешанный** период считается по **km-доске weryfikatora** (тот же источник, что у перевозчика, — SpedTrans, только по дням; [20 §0⁵](20-phase-7-eksport-weryfikator.md)):

```
все недели с kmPerDay > 0:
  mileageEffective = przebieg                                   // mileageSource = 'declared'
есть неделя с kmPerDay = 0:
  mileageEffective = Σ VehicleDailyKm.km (state = drove)        // mileageSource = 'board'
                     по дням периода [dateStart … dateEnd] (включительно),
                     которые засчитываются в своей неделе (см. ниже)
roznica          = kmGwarant − mileageEffective
doplata          = roznica > 0 ? round2(roznica × ratePerKmEffective) : 0
```

Какие дни засчитываются, по неделям ISO периода:

| Неделя | Условие | Засчитываются |
|---|---|---|
| активная | `kmPerDay > 0` | **каждый** календарный день недели в пределах периода: воскресенье, праздники EU-бана, незачтённая суббота; первый и последний день — целиком (`timeFrom`/`timeTo` укорачивают гарантию, а не км) |
| «tylko sobota» | `kmPerDay = 0`, `kmPerSaturday > 0` | только суббота недели, если она засчитана (`saturdayDays`) |
| выключенная | `kmPerDay = 0`, `kmPerSaturday = 0` | ничего |

- **Все недели включены** → доска даже не читается, числа побитово совпадают с прежней `kmGwarant − przebieg`. Это подавляющее большинство wniosków.
- В смешанном периоде цифра перевозчика (`mileage`) на выплату **не влияет** — она остаётся для сверки с доской.
- **Незаписанный день не угадывается.** «Строка» — отметка weryfikatora за `(машина, день)`: `drove` с км или `idle` (заполненный день, 0 км; `drove` без км — тоже 0). Засчитываемый день без строки даёт 0 км и попадает в `missingDates`: подачу это не блокирует (типично — день съезда, который доска даёт заполнить только назавтра), а **принятие** (`ZAAKCEPTOWANO`) блокирует — 422 `CLAIM_BOARD_INCOMPLETE`, пока weryfikator не допишет. «Zapisz weryfikację» с дырами сохраняет числа и ставит `verifiedAt` (`ODRZUCONO` доступен), но не взводит гейт Maksima и не двигает статус. Дыра в выключенной неделе ни на что не влияет.
- **Доска живая и не замораживается** в `breakdown` (в отличие от лимитов). Выплата смешанного периода пересчитывается по доске на превью, при подаче, при каждом «Zapisz weryfikację» и **при решении**: wniosek принимается с суммой по доске на момент решения. Если она разошлась с сохранённой при верификации (или над порогом без снятого на эту сумму гейта) — 422 `CLAIM_BOARD_CHANGED`, верификацию нужно сохранить заново. В `breakdown` пишется только `mileageSource` и `mileageEffective`; понедельная доска (`boardSettlement`) отдаётся staff'у на чтении ([13-api-design.md](13-api-design.md#claims-wnioski--apiv1claims)).
- Что **не** меняется: `drivenDays` и `kmPerDay` на wniosku считаются по **полному** периоду и цифре перевозчика (это фактическая средняя выезда), санитарная проверка `max_avg_km_per_day` — на сыром `przebieg / totalDays`, порог подачи (≥10 дней) — на `totalDays`. `daysActive`/`daysTotal` (зачтённые дни с гарантией / все зачтённые дни) сохраняют прежний смысл — по ним UI решает, показывать ли подсказку о выключенной гарантии.
- Реализация — одна: `packages/shared/src/domain/claim-settlement.ts` (`settleClaim`, `settlementNeedsBoard`); api читает доску (`VehicleDailyKmRepository.listBoardDays`) только когда `settlementNeedsBoard` истинно.

Пример (08.06–21.06.2026, неделя W24 08.06–14.06 выключена, W25 15.06–21.06 включена — 5 будних дней × 540 = 2700 км, суббота без гарантии, 0,50 €/км, перевозчик вписал 3500): доска «W24 2000 / W25 1500» → `mileageEffective = 1500`, `roznica = 1200`, выплата **600 €**; доска «500 / 3000» → `roznica = −300`, выплата **0 €**.

**Заморозка лимитов.** Суммы поданного wniosek-а считаются по снимку лимитов, зафиксированному в его `breakdown` при подаче (по неделям, ключ `YYYY-Www`): пересчёты (правки верификатора, авто-пересчёт по выезду, превью существующего wniosek-а) **не** подхватывают задним числом изменённые `weekly_limits`. Единственный явный выход — `POST /claims/:nrZgl/recalc-limits` (`admin`/`pracownik`, только для `NA_WERYFIKACJI`), который пересчитывает по актуальным лимитам и пишет audit `claim.limitsRefresh`. Перед записью веб показывает diff «было → станет» из dry-run `GET /claims/:nrZgl/recalc-limits/preview` (тот же расчёт и тот же гейт, но без записи): итоги в км и EUR плюс список недель, у которых изменились лимиты.

### Авторизация крупной суммы

Если при zapisie weryfikacji финальная `paymentEur > getAuthThreshold(drivenDays)` — заявление **автоматически** переходит в `OCZEKUJE_NA_AUTORYZACJE` («Czeka na autoryzację»), Maksim'у уходит письмо-подтверждение (dedup по сумме), а решение блокируется (422 `CLAIM_AUTHORIZATION_REQUIRED`) до загрузки screenshot-а его ответа. Ручной отправки на авторизацию не существует; правка, уводящая сумму под порог, автоматически возвращает заявление в `NA_WERYFIKACJI`. Threshold — step-функция от количества дней в трассе:

| `drivenDays` | Threshold (EUR) |
|---|---|
| ≥ 61 | 1000 |
| 31..60 | 800 |
| 16..30 | 500 |
| 10..15 | 300 |

Подробности процесса (screenshot upload, audit trail) — см. [19-known-quirks.md](19-known-quirks.md#getAuthThreshold). Эти константы пока зашиты в коде; backlog — вынести в `AppConfig` или новую таблицу.
