# 29. План: передача машины другому планисте (заявка → апрув) и история планистов

> **Статус: РЕАЛИЗОВАНО (2026-09-28)** — db, api, web, доки; на pre-prod ещё
> не выкачено (§8). Механизм, который
> [28-lider-roles-plan.md](28-lider-roles-plan.md) §6 отложил «до отдельного
> плана». Решения пользователя — §1, маршрутизация по агентам — §5 (orchestrator,
> 2026-09-28). §0 описывает поведение **до** фичи. Что теперь описывает
> систему: [03](03-roles.md) (planista, opiekun, admin, лидеры),
> [13](13-api-design.md) «Vehicle planner transfers», [14](14-design-system.md)
> §17 (+ отступления web §17.15), [19](19-known-quirks.md) #14, #15; отступления
> реализации от этого плана — §11.

## 0. Как сейчас

- `Vehicle.plannerId` меняет `PATCH /vehicles/:id` (`@Roles('admin','opiekun')`,
  opiekun — только машины своих перевозчиков). Проверка одна: цель — активный
  `planista` (`vehicles.service.ts#_assertRole`). Побочных действий нет.
- Всё, что связано с планистой, читается **живьём** из `vehicle.plannerId`:
  список и карточка выездов, флот, GPS, отчёт по км, получатели писем по
  wnioskam (`planner.email` + `planner.liderEmail`), имя планисты в Chat-сообщении
  о выезде, блок «ZESPÓŁ PROWADZĄCY».
- Следствие: после смены старый планиста сразу теряет всю историю машины
  (включая выезды, которые вёл), новый видит её целиком; письма по старым
  wnioskam уходят новому планисте и его лидеру. Истории назначений нет, кроме
  строки в `/employee/audit`.
- «Кто чей лидер» не хранится: `User.liderEmail` — только e-mail для CC
  ([19](19-known-quirks.md) #14), `User.lider` — флаг без прав ([28](28-lider-roles-plan.md)).

## 1. Решения

### 1.1 Решения пользователя (2026-09-28)

| ID | Решение |
|---|---|
| R1 | Напрямую планисту не меняет **никто** — ни opiekun, ни admin, ни лидер. Только заявкой |
| R2 | Заявку подают: **opiekun** перевозчика машины и **текущий планиста** машины |
| R3 | Решают (одобрить / отклонить): **admin** или **лидер текущего планисты**. Лидер другого планисты, в том числе лидер планисты-получателя, решать не может |
| R4 | Автор заявки и планиста-получатель решить её не могут — тогда решает только admin. У планисты нет лидера — тоже только admin |
| R5 | История сохраняется: каждый выезд помнит планисту своего периода. Старый планиста продолжает видеть выезды, которые вёл, новый видит только выезды после передачи. Письма по wnioskam идут планисте периода. Плюс журнал назначений по машине |
| R6 | При одобрении невыехавшие выезды (`zgloszony`, `gotowy`) переходят новому планисте. Выезд в статусе `w_trasie` доводит старый до возврата. `zjechal` / `anulowany` остаются за старым |
| R7 | Первого планисту машина получает **при создании**, сразу (opiekun / admin в форме создания, как сейчас). Все последующие смены — только заявкой |
| R8 | `liderEmail` заменяется связью `User.liderId`. Миграция переносит совпавшие e-mail и печатает несовпавшие; колонка удаляется **отдельным релизом** после проверки |
| R9 | Уведомлений нет: ни писем, ни Chat-сообщений о заявках и решениях |

### 1.2 Умолчания (приняты в плане, можно поменять)

| ID | Умолчание |
|---|---|
| U1 | Admin заявку **не подаёт** — иначе «подал и сам одобрил» равно прямой смене (R1). Admin только решает |
| U2 | Цель передачи — любой активный планиста, кроме текущего |
| U3 | Причина обязательна при подаче и при отклонении; комментарий к одобрению — по желанию |
| U4 | На машину — не больше одной заявки в статусе `pending`. Автор может отменить свою `pending`-заявку |
| U5 | Передача вступает в силу сразу при одобрении, без даты «с какого числа» |
| U6 | Одобрение перепроверяет всё заново: заявка ещё `pending`, текущий планиста машины не сменился (иначе 409), получатель — активный планиста, машина активна. Деактивация машины отменяет её `pending`-заявку |
| U7 | Экраны уровня машины остаются **живыми** по текущему планисте: флот, GPS, отчёт по км, список и карточка машины. Старый планиста теряет машину в этих экранах сразу, включая прошлые недели км. Исторические — только выезды, получатели писем по wnioskam и имя в Chat-сообщении |
| U8 | Получатели писем по wniosku: планиста из снимка выезда wniosku; если выезда нет — все планисты, чьи периоды назначения пересекают `[dateStart, dateEnd]`. CC — **текущий** лидер каждого из них (`liderId → email`) |
| U9 | `liderId` ставит только admin (MAGSpace иерархии не отдаёт, reconcile поле не трогает). Только у `planista`; цель — активный `planista` с `lider = true`, не он сам |
| U10 | Снятие флага `lider` (admin или reconcile) не очищает `liderId` у подчинённых. Но решать может только тот, у кого `lider = true` **в момент решения** — иначе заявки его планистов решает admin |
| U11 | Кто что видит. Журнал назначений машины — admin, opiekun перевозчика, текущий планиста, лидер текущего планисты; przewoznik — нет. Входящие заявки — admin все, лидер — заявки своих планистов, автор — свои. Планиста-получатель до одобрения заявку не видит |

## 2. Модель данных — db-agent

Имена таблиц и колонок — на усмотрение db-agent.

1. **`User.liderId`** — self-FK на `User`, `ON DELETE SET NULL`, индекс.
   Правило «цель — planista с `lider = true`» межстрочное, CHECK его не
   выразит: проверяет api (как `teamId`), в схеме — комментарий.
   Бэкфилл из `liderEmail`: регистронезависимое совпадение с пользователем
   `role = planista AND lider = true`. Миграция печатает число строк без
   совпадения. `liderEmail` в этом релизе остаётся (не читается), удаляется
   следующим (R8).
2. **`Delegation.plannerId`** — снимок планисты выезда: nullable FK на `User`
   со своим именем связи, индекс под scope планисты (`plannerId` + `status`
   или `departureAt`). Бэкфилл из текущего `vehicle.plannerId`.
3. **Заявки на передачу** (append-only): машина, `fromPlanner`, `toPlanner`,
   `requestedBy`, статус `pending | approved | rejected | cancelled`, причина,
   комментарий решения, `decidedBy`, `decidedAt`, `createdAt`. Частичный
   уникальный индекс: одна `pending` на машину (сырой SQL в миграции).
4. **Журнал назначений** (append-only): машина, планиста, `validFrom`,
   `validTo` (NULL = текущий), источник `create | transfer | backfill`, ссылка
   на заявку, актор. Частичный уникальный индекс: одна открытая строка на
   машину. Бэкфилл: по одной открытой строке на машину с планистой,
   `validFrom = vehicle.createdAt`, источник `backfill`.
5. **`Vehicle.plannerId` остаётся** указателем на текущего планисту. Инвариант:
   он равен планисте открытой строки журнала. Поэтому живые запросы уровня
   машины (U7) не меняются.
6. Обе новые таблицы — append-only, в allowlist soft-delete-расширения их нет
   (как `GuaranteeIdleEpisode`).
7. Сид: планистам проставлен `liderId → planistalider1`; один планиста без
   лидера (его заявки решает только admin); заявки во всех статусах; машина с
   двумя строками журнала и выездами по обе стороны передачи.
8. Миграция аддитивная, forward-only, бэкфиллы идемпотентные — должна пройти
   на уже заполненной базе pre-prod.

> **Ограничение бэкфилла.** Кто вёл машину до этой фичи, неизвестно. Бэкфилл
> считает, что все прошлые выезды вёл текущий планиста. Точная история
> начинается с момента выката.

## 3. API — api-agent (shared + api одним набором изменений)

### 3.1 Контракты

- `PATCH /vehicles/:id` с `plannerId` → **422** с кодом
  `VEHICLE_PLANNER_CHANGE_REQUIRES_TRANSFER` (не молча выбросить поле). Для
  всех ролей, включая admin (R1). Возможность «снять планисту» (`null`)
  исчезает.
- `POST /vehicles` — без изменений: `plannerId` обязателен (R7), плюс строка
  журнала с источником `create`.

| Метод | Путь (ориентир) | Кто | Что |
|---|---|---|---|
| POST | `/vehicles/:id/planner-transfers` | opiekun (свой перевозчик), планиста (текущий на машине) | подать заявку; 409, если уже есть `pending` |
| GET | `/vehicles/:id/planner-history` | см. U11 | журнал назначений + заявки по машине |
| GET | `/planner-transfers?status=` | admin — все; планиста-лидер — своих планистов; автор — свои | входящие / мои заявки |
| POST | `/planner-transfers/:id/approve` | admin; лидер `fromPlanner` | одобрить |
| POST | `/planner-transfers/:id/reject` | admin; лидер `fromPlanner` | отклонить (причина обязательна) |
| POST | `/planner-transfers/:id/cancel` | автор | отменить свою `pending` |

**Авторизация решения** — проверка на уровне ресурса в сервисе, а не guard:
`@Roles('admin','planista')`, затем
`user.role === 'admin' || (user.lider && fromPlanner.liderId === user.sub)`,
и в любом случае `user ≠ requestedBy` и `user ≠ toPlanner` (R4). Поэтому ни
`LiderGuard`, ни B1–B2 трека B ([25](25-permissions-layer-plan.md)) для этой
фичи не нужны.

### 3.2 Транзакция одобрения

1. Заблокировать строку машины.
2. Проверить U6: заявка `pending`; `vehicle.plannerId === fromPlannerId`
   (иначе 409 «устарела»); `toPlanner` — активный планиста; машина активна.
3. `Vehicle.plannerId = toPlanner`; закрыть открытую строку журнала
   (`validTo = now`), открыть новую (источник `transfer`, ссылка на заявку).
4. Выезды машины со статусом `zgloszony` / `gotowy` и
   `plannerId = fromPlanner` → `toPlanner` (R6).
5. Заявка → `approved`, `decidedBy`, `decidedAt`.
6. Audit-записи с новыми action-именами (подача / одобрение / отклонение /
   отмена). Писем и Chat нет (R9).

### 3.3 Где читается планиста — что меняется

| Место | Сейчас | После |
|---|---|---|
| Создание выезда (`DelegationsService.add`) | — | ставит снимок `Delegation.plannerId = vehicle.plannerId` |
| Scope выездов планисты: список и карточка (`delegations.service.ts` ≈L741, ≈L1067; repository ≈L311–316) | `vehicle.plannerId` | `delegation.plannerId` |
| «ZESPÓŁ PROWADZĄCY» в DTO выезда (repository ≈L439, ≈L493; shared `delegations.ts` ≈L465 — комментарий «resolved LIVE») | `vehicle.planner` | `delegation.planner` |
| Имя планисты в Chat-сообщении о выезде (`chat.repository.ts` ≈L94, ≈L130) | `vehicle.planner.name` | `delegation.planner.name` |
| Получатели писем по wniosku (`claims.service.ts#_collectClaimRecipients` ≈L3578–3586) | `vehicle.planner.email` + `liderEmail` | U8 |
| Флот, GPS, отчёт по км, список и карточка машины | живьём | **без изменений** (U7) |

### 3.4 Users, lookups, reconcile

- `liderId` в создании и правке пользователя, фильтр; `UserDto` — `liderId` +
  мини-объект лидера; `liderEmail` из DTO уходит. Валидация U9 — 422 с кодом.
- Lookups: пикер активных планистов-лидеров (для UserSheet); пикер цели
  передачи — активные планисты без текущего.
- `directory-reconcile` `liderId` не трогает (U9, U10).

### 3.5 Тесты (минимум)

- Матрица решения: admin ✓; лидер `fromPlanner` ✓; лидер получателя ✗;
  другой лидер ✗; обычный планиста ✗; лидер-автор ✗; лидер-получатель ✗;
  лидер с `lider = false` ✗.
- Подача: opiekun чужого перевозчика ✗; не текущий планиста ✗; admin ✗ (U1);
  вторая `pending` → 409.
- Одобрение: конкурентные одобрения / устаревшая заявка → 409; перенос
  `zgloszony`/`gotowy` и неперенос `w_trasie`/`zjechal`.
- `PATCH /vehicles` с `plannerId` → 422.
- Видимость выездов старым и новым планистой до и после передачи.
- Получатели писем для wniosku с выездом и без него, с периодом через
  передачу.
- Бэкфиллы на фикстурах формы pre-prod; отчёт о несовпавших `liderEmail`.

## 4. UI — uiux-agent (спека в docs/14) → web-agent

- **`VehicleFormDialog.tsx`**: выбор планисты — только при создании. При
  правке планиста только для чтения + кнопка «Poproś o zmianę planisty»
  (диалог: цель + причина) + бейдж ожидающей заявки. PATCH никогда не шлёт
  `plannerId`.
- **Панель планисты** (`/planista/moje-pojazdy`): «Przekaż pojazd» у своих
  машин; «Moje wnioski o przekazanie».
- **Входящие на решение**: admin — в `/employee/…`; планиста-лидер — в
  `/planista/…`, пункт меню только при `user.lider`. Это первый пункт меню,
  зависящий от лидерства — осознанное отступление от docs/28 §3.4. Edge
  middleware не импортирует shared (docs/28 §9.2 #18). Счётчик `pending` у
  пункта меню — не уведомление (R9), а единственный способ узнать о заявке;
  убрать, если не нужен.
- **Журнал назначений** в карточке машины: кто, с какого по какое, от кого к
  кому, кто подал, кто одобрил.
- **`UserSheet.tsx`**: текстовое поле «E-mail lidera (CC)» → выбор «Lider»
  (только для планистов).
- **Модалка выезда**: планиста из снимка.
- i18n PL/EN; инвалидация запросов машин, выездов и входящих после решения.

## 7. Конфликты с существующими доками

2. **docs/28 §5** — до первого лидерского эндпоинта сделать B1–B2 или
   временный `LiderGuard`. Не нужно: «лидер именно этого планисты» — проверка

   меню.
4. **docs/03** — планиста «ничего не редактирует», «выезды своих авто»
   (живьём); admin правит `plannerId`; лидер «ничего сверх базовой роли»;
   `liderEmail`.
5. **docs/13** (Delegations: «planista → свой `plannerId`») и комментарии в
   shared `delegations.ts` (≈L465, «resolved LIVE») и `claims.ts` (≈L151,

## 8. Выкат

- Миграция с бэкфиллами → перед выкатом на pre-prod **ручной бэкап**
  (docs/26 «Режим эксплуатации» п. 4).
- После выката — через `preprod-parity-agent`: проверить отчёт миграции о
  несовпавших `liderEmail`; admin проставляет `liderId` планистам в UserSheet
  (до этого все заявки решает только admin); строка-пара для prod в
  docs/27.
- Удаление колонки `liderEmail` — отдельный релиз после проверки (R8, правило
  docs/23 «Откат»: удаление колонки — отдельным релизом).

## 9. Не делаем

- Трек B ([25](25-permissions-layer-plan.md)), `RolesGuard`, переход
  `@Roles` → permissions.
- Расширение scope лидера (видеть все машины своих планистов) — docs/28 §8
  вопрос 2, часть про видимость.
- Историческую видимость флота, GPS, отчёта по км, списка машин (U7).
- Передачу dispatch-команды (`dispatchTeamId`) и лидеров других ролей.
- Отложенные передачи «с даты», автоистечение заявок, SLA.

## 10. Открытые вопросы

1. Нужно ли admin право **подать** заявку — например, когда opiekun в
   отпуске, а планиста уволен? Сейчас нет (U1): такую машину admin передать
   не может, пока заявку не подаст opiekun.
2. Сроки относительно запуска (Фаза 10 docs/17) — до или после. Не блокирует.
3. **Машина без планисты не может его получить.** `PATCH` с `plannerId`
   запрещён, а заявке нужен текущий планиста (422
   `PLANNER_TRANSFER_NO_CURRENT_PLANNER`). Такие машины есть (создание
   требует планисту, но старые строки и dev-база содержат `plannerId = NULL`).
   Варианты: разрешить первое назначение через `PATCH`, только когда
   `plannerId IS NULL` (строка журнала `create`), — это в духе R7; или
   исправлять данные вручную. **2026-09-28: не актуально** — на pre-prod машин
   нет (только пара аккаунтов), создание машины требует планисту, а dev-сид
   теперь ставит планисту всем демо-машинам. Вернуться, только если такие строки
   появятся.

## 11. Отступления реализации от плана (2026-09-28)

- **Закрытие заявки при выключении машины** расширено (U6): отменяют
  `pending`-заявку не только деактивация, но и `PATCH active=false`, soft-delete
  машины и удаление перевозчика (вся его флота). `decidedById` = кто выключил.
- **Получатели писем (U8):** неактивные и удалённые планисты и лидеры больше не
  получают писем (раньше планисте слали всегда). Последний день периода wniosku
  считается целиком — передача в этот день шлёт обоим. Если у выезда wniosku
  снимок пустой, к пересечению журнала **не** откатываемся.
- **«Nadaj dostęp»** (SSO) при выдаче роли не-`planista` тоже очищает `liderId`
  аккаунта (как `PATCH /users`).
- **Схема:** шесть CHECK сверх плана (from≠to, непустая причина,
  `pending ⇔ decidedAt IS NULL`, отказ с комментарием, `validTo ≥ validFrom`,
  `transfer ⇔ transferId`); журнал → машина `ON DELETE CASCADE` (только ради
  отката создания машины при провале загрузки вложений); `decidedAt/By` пишутся
  и при `cancelled` (= автор).
- **Отчёт бэкфилла** `liderEmail` выводится `RAISE NOTICE`, который
  `prisma migrate deploy` не показывает. Тот же отчёт — SQL-запросом из docs/12
  после выката (§8).
- **UI** — отступления D1–D8 (docs/14 §17.0) и W1–W18 (§17.15): «ciągnik» вместо
  «pojazd», вкладки панели планисты, пункт «Przekazania» у opiekuna, стек
  диалогов (Esc закрывает только верхний), `LockNotice` отдаётся `<div>`, а не
  `<p>` (в диалоге одобрения внутри список).
